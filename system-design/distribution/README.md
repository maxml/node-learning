# Приклади: консистентне хешування, балансування, ідентифікатори

Код експериментів, на які спираються нотатки
`Obsidian Vault/Engineering/General/System design/Консистентне хешування.md`,
`System design/Балансування навантаження.md` і `System design/Генерація ідентифікаторів.md`.

**Застереження.** `hashing.js` і `lb_sim.js` це моделі (розподіл ключів і дискретна
симуляція черг), а не виміри продакшн-систем: вони показують напрям і порядок ефекту.
Виміри в PostgreSQL і MongoDB зроблено на одному ноутбуці в Docker; секунди між прогонами
плавають до 30%, тож порівнювати варто розміри індексів, щільність листків і WAL, а час
лише як напрям.

| Файл           | Що перевіряє                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| `hashing.js`   | частка переїзду ключів при N → N+1 і при видаленні вузла; розкид ключів max/mean для mod N, кільця з 1/10/100/1000 віртуальних вузлів, rendezvous, jump hash, Maglev; ключі проти навантаження за Zipf |
| `lb_sim.js`    | round robin, random, least connections, P2C, P2C + peak-EWMA: різна вартість запитів, повільний сервер, сервер-«чорна діра» з outlier detection і без, L4-пінінг довгих з'єднань проти L7 |
| `ids_node.js`  | `crypto.randomUUID()` і `uuid@14` (версії, монотонність v7, вартість генерації), будова `ObjectId`, межі Snowflake |
| `ids_pg.js`    | 1M вставок з ключем `bigint` identity, UUIDv4 і UUIDv7 (з Node і `uuidv4()`/`uuidv7()` на сервері): час, WAL, розмір PK-індексу, щільність листків (`pgstatindex`) |
| `ids_mongo.js` | 1M вставок з `_id` = ObjectId, UUIDv4, UUIDv7 (BSON Binary subtype 4), Int64-лічильник: час і `indexSizes._id_` після checkpoint |
| `run.sh`       | усе разом; контейнери `sd-pg`, `sd-mongo` видаляються наприкінці (крім `KEEP=1`)                                   |

## Запуск

Потрібні Node.js 24 і Docker. Образи закріплено за digest: `postgres:18` = 18.6,
`mongo:9` = 9.0.4. Залежності (`uuid` 14.0.3, `pg` 8.23.1, `mongodb` 7.7.0) ставляться лише в
цю теку.

```bash
cd examples/system-design/distribution
npm ci
bash run.sh                 # ~15 хв (5M-прогін PostgreSQL ~4 хв); результати в out/*.md
KEEP=1 bash run.sh          # лишити контейнери для ручних дослідів
node hashing.js             # окремо, без Docker (~20 с)
SEED=7 node lb_sim.js       # інший seed для симуляції
```

Порти: PostgreSQL 55461, MongoDB 27061 (`PG_PORT`, `MONGO_PORT`).

### Балансування (10 серверів × 4 воркери, 300 000 запитів, 95% по 5 мс і 5% по 200 мс)

| Сценарій                                   | RR             | random         | least conn.    | P2C            | P2C + peak-EWMA |
| ------------------------------------------ | -------------- | -------------- | -------------- | -------------- | --------------- |
| A. рівні сервери, 70%: p99 / p99,9 мс       | 249 / 374      | 260 / 369      | 200 / 200      | 200 / 208      | 200 / 209       |
| B. один сервер ×4 повільніший: p99 мс       | 260 582        | 262 952        | 200            | 202            | 202             |
| C. один сервер віддає помилку за 1 мс: помилок | 10,00%      | 10,05%         | 45,15%         | 19,07%         | 20,12%          |
| C+. те саме + outlier detection: помилок    | 0,01%          | 0,01%          | 0,01%          | 0,01%          | 0,01%           |

D. 20 довгих з'єднань із Zipf(1)-інтенсивністю (топ-з'єднання 27,8% запитів), 50%:
балансування з'єднань (L4) дало p99 116 557 мс і 154% ємності на найзайнятішому сервері;
балансування запитів (L7, P2C) дало p99 200 мс і 50%. На seed 7 і 99 частки помилок у C
збіглися до десятих відсотка (45,3% / 19,2% і 45,3% / 18,9%).

### Ідентифікатори в Node

- `crypto.randomUUID()` повертає версію 4; `crypto.randomUUIDv7` у Node 24.14.1 `undefined`
  (у документації Node він з'являється у v26.1.0).
- `uuid@14` `v7()`: 200 000 ідентифікаторів підряд строго зростають як рядки (932 різні мс).
- Генерація 1M: `crypto.randomUUID()` 0,12 с, `uuid` `v4()` 0,39 с, `uuid` `v7()` 4,89 с,
  `new ObjectId()` 0,11 с. Тобто в клієнтських вставках UUIDv7 частина часу йде на саму генерацію.
- `ObjectId`: два підряд з одного процесу мають однакові 5 байт процесу й лічильник +1.
- Snowflake: 41 біт мілісекунд = 69,7 року від власної епохи; 4096 id/мс на воркер; 1024 воркери.

### Індекси в PostgreSQL

1 млн рядків, медіана трьох прогонів (секунди: медіана; розміри від прогону до прогону
збігаються до десятих МБ):

| Ключ               | 128 МБ: вставка, с | 16 МБ: вставка, с | WAL, МБ | PK-індекс, МБ | Щільність листків | Таблиця, МБ |
| ------------------ | ------------------ | ----------------- | ------- | ------------- | ----------------- | ----------- |
| `bigint` identity  | 4,13               | 4,73              | 165,7   | 21,4          | 90,0%             | 80,5        |
| UUIDv4 з Node      | 6,87               | 12,42             | 192,9   | 37,8          | 71,8%             | 88,8        |
| UUIDv7 з Node      | 8,23               | 9,86              | 179,8   | 30,1          | 90,0%             | 88,8        |
| `uuidv4()` сервер  | 7,44               | 13,41             | 192,6   | 37,2          | 72,8%             | 88,8        |
| `uuidv7()` сервер  | 5,68               | 7,08              | 179,2   | 30,1          | 90,0%             | 88,8        |

5 млн рядків, `shared_buffers` 16 МБ, генерація на сервері, один прогін:

| Ключ              | Вставка, с | WAL, МБ | PK-індекс, МБ | Щільність листків |
| ----------------- | ---------- | ------- | ------------- | ----------------- |
| `bigint` identity | 30,04      | 835,6   | 107,1         | 90,0%             |
| `uuidv7()` сервер | 42,65      | 895,7   | 150,4         | 90,0%             |
| `uuidv4()` сервер | 131,21     | 1446,7  | 190,1         | 71,2%             |

`uuidv7()` ×100 000 в одному запиті строго зростають (247–310 різних мілісекунд за
прогони); `uuid_extract_version` дає 7 для `uuidv7()` і 4 для `gen_random_uuid()` та `uuidv4()`.
Порядок рядків «UUIDv4 з Node» і «UUIDv7 з Node» за часом спотворений вартістю генерації
`uuid@14` `v7()` (~5 с на мільйон), тому для порівняння беріть серверні рядки.

### Індекси в MongoDB (WiredTiger, `indexSizes._id_` після `fsync`)

| `_id`             | кеш 15 465 МБ: вставка, с | індекс `_id`, МБ | кеш 256 МБ: вставка, с | індекс `_id`, МБ |
| ----------------- | ------------------------- | ---------------- | ---------------------- | ---------------- |
| ObjectId          | 7,85                      | 10,3             | 7,61                   | 10,3             |
| UUIDv4 (Binary 4) | 12,03                     | 35,3             | 16,62                  | 30,6             |
| UUIDv7 (Binary 4) | 13,60                     | 19,3             | 13,65                  | 19,6             |
| Int64 лічильник   | 7,17                      | 12,5             | 6,01                   | 12,5             |

Час вставки UUIDv7 включає ~4,9 с генерації в `uuid@14` на мільйон (див. вище), тож без неї
UUIDv7 вставляється швидше за UUIDv4. Розмір індексу від генерації не залежить: UUIDv4 дав
індекс `_id` у 1,6–1,8 раза більший за UUIDv7 і в 3–3,4 раза більший за ObjectId.
