# Стійкість, rate limiting, оцінка навантаження: експерименти

Код за позначками «перевірено» в нотатках `Obsidian Vault/Engineering/General/System design/`:
`Патерни стійкості.md`, `Rate limiting.md`, `Оцінка навантаження.md`.

Середовище прогону 2026-10-30: Node.js 24.14.1, Valkey 9.1.3 (`valkey/valkey:9.1.3-alpine`),
npm-пакети з точними версіями в `package.json`: opossum 10.0.0, ioredis 6.0.0,
rate-limiter-flexible 11.2.3. Linux 6.8, loopback. Залежності ставляться лише в цю теку.

## Запуск

```bash
npm ci                                   # або npm install
node retry-storm.mjs                     # симуляція, без мережі; SEEDS=42,1,2 для кількох зерен
node amplification.mjs                   # ланцюжок HTTP-сервісів
node deadline.mjs                        # таймаут з AbortSignal і без
node circuit-breaker.mjs                 # opossum перед «мертвою» залежністю
node ratelimit-algos.mjs                 # алгоритми на віртуальному годиннику
docker run -d --name sd-resilience-valkey -p 127.0.0.1:6390:6379 valkey/valkey:9.1.3-alpine
node ratelimit-redis.mjs                 # атомарність на Valkey
docker rm -f sd-resilience-valkey
node littles-law.mjs                     # L = λW на HTTP-сервері
node utilisation.mjs                     # утилізація → латентність; RHO=0.9,0.95 SECONDS=90 для довгих прогонів
```

## Що це за експерименти і чого вони не доводять

- `retry-storm.mjs` це **дискретно-подієва симуляція** у віртуальному часі із зерном, а не
  навантаження на справжній сервіс. Модель (W воркерів, черга FIFO, клієнтський таймаут, сервер
  доробляє покинуті запити) повторює приклад з Bronson et al., *Metastable Failures in Distributed
  Systems* (HotOS 2021). Числа описують цю модель; напрям висновків переноситься, конкретні
  мілісекунди ні.
- `ratelimit-algos.mjs` теж на віртуальному годиннику: алгоритм від цього не залежить.
- Решта (`amplification`, `deadline`, `circuit-breaker`, `ratelimit-redis`, `littles-law`,
  `utilisation`) працює з реальними сокетами, таймерами й Valkey, але на одній машині.

## Результати 2026-10-30

### 1. Retry storm і метастабільна відмова (`retry-storm.mjs`, зерно 42)

Залежність: 10 воркерів по 10 мс (місткість 1000 rps), навантаження 700 rps (70%), з 2-ї по 3-тю
секунду обслуговування в 10 разів повільніше (100 rps), клієнтський таймаут 150 мс, до 3 спроб,
30 с прогону. «Відновився» означає: з цього моменту кожні 500 мс успішних ≥ 95%.

| політика | викликів | на логічний запит | успішних | відновлення після тригера | марна робота сервера |
| --- | ---: | ---: | ---: | --- | ---: |
| без ретраїв | 20 846 | 1,00 | 91,3% | 2,0 с | 1 762 |
| миттєві ретраї (×3) | 59 754 | 2,87 | 6,9% | не відновився до кінця прогону (26 с після тригера) | 28 071 |
| exp backoff 50 мс·2ⁿ | 59 754 | 2,87 | 6,9% | не відновився | 28 071 |
| backoff + full jitter | 59 754 | 2,87 | 6,9% | не відновився | 28 071 |
| backoff + jitter + бюджет ретраїв 10% | 21 082 | 1,01 | 88,8% | 2,5 с | 2 494 |
| миттєві + сервер відкидає прострочені (FIFO) | 59 754 | 2,87 | 6,9% | не відновився | 27 394 |
| миттєві + LIFO + відкидання прострочених | 22 124 | 1,06 | 97,7% | одразу | 0 |
| миттєві + черга ≤ 150, далі швидкий 503 | 22 251 | 1,07 | 96,6% | одразу | 249 |
| jitter + бюджет 10% + черга ≤ 150 | 20 926 | 1,00 | 96,5% | одразу | 251 |

На зернах 1 і 2 картина та сама, з одним винятком: «миттєві + черга ≤ 150» на зерні 2 **не
відновилась** (9,6% успішних). Обмежена черга без бюджету ретраїв нестабільна; з бюджетом
відновлення стабільне (0–0,5 с на всіх трьох зернах).

Висновки моделі: backoff і jitter не зменшують кількість спроб запиту, який однаково впаде, тож
проти посилення навантаження ретраями вони не допомагають; допомагає обмеження *частки* ретраїв
(бюджет) і відмова від роботи, на яку вже ніхто не чекає (LIFO + відкидання прострочених,
обмежена черга).

### 2. Синхронізовані клієнти і jitter (`retry-storm.mjs`, частина B, зерно 42)

100 клієнтів стартують одночасно, база 10 мс, cap 1 с, до 50 спроб.

Модель «конкуренція» (один ресурс, успішний виклик тримає його 2 мс, як OCC-рядок у Brooker 2015):

| політика | викликів | завершення | здались |
| --- | ---: | ---: | ---: |
| миттєвий ретрай | 4 375 | — | 75 зі 100 |
| exp backoff без jitter | 3 775 | 43,3 с (половина здалась) | 50 |
| equal jitter | 555 | 0,99 с | 0 |
| full jitter | 548 | 1,0 с (0,5–1,0 с на зернах 1, 2) | 0 |

Модель «ліміт 200 rps, burst 20»: backoff без jitter 488 викликів і 1,28 с; equal jitter 475 і
0,56 с; full jitter 504 і 0,85 с. Проти чистого ліміту швидкості jitter скорочує час, але не
кількість викликів.

### 3. Посилення ретраями по глибині (`amplification.mjs`)

Клієнт → A → B → C → D, D завжди відповідає 503, кожен рівень, що ретраїть, робить 3 спроби:

| хто ретраїть | викликів до D на одну дію |
| --- | ---: |
| лише клієнт | 3 |
| клієнт + A | 9 |
| клієнт + A + B | 27 |
| усі чотири рівні | 81 |

### 4. Таймаут без поширення дедлайну (`deadline.mjs`)

Нижній сервіс робить 10 кроків по 100 мс, бюджет викликача 300 мс:

| варіант | що побачив викликач | кроків виконав нижній сервіс |
| --- | --- | ---: |
| `Promise.race` з таймером, без abort | gave up, 310 мс | 10 з 10 |
| `fetch(..., { signal: AbortSignal.timeout(300) })`, сервер не слухає `close` | `TimeoutError`, 304 мс | 10 з 10 |
| те саме, сервер прив'язує роботу до `res.on('close')` | `TimeoutError`, 300 мс | 2 з 10 |
| `Promise.race` без abort, але з заголовком дедлайну; сервер `AbortSignal.any([close, timeout(залишок)])` | 504, 302 мс | 2 з 10 |

### 5. Circuit breaker (`circuit-breaker.mjs`, opossum 10.0.0)

Залежність 3 с не відповідає (висить), потім відповідає за 5 мс; виклик кожні 20 мс протягом 6 с,
таймаут 500 мс; breaker: `errorThresholdPercentage: 50`, `volumeThreshold: 10`, `resetTimeout: 1000`.

| | без breaker | з breaker |
| --- | ---: | ---: |
| викликів до залежності, поки вона мертва | 145 | 50 |
| швидких відмов breaker-а | 0 | 121 |
| латентність викликача, поки мертва: p50 | 500,6 мс | 0,1 мс |
| p99 | 502,1 мс | 502,0 мс |
| найбільше одночасних запитів, що висять на залежності | 25 | 25 |
| перший успіх після оживлення | +2 мс | +516 мс |

Переходи: `open@994 halfOpen@1994 open@2500 halfOpen@3501 close@3522` (мс від старту). Breaker
відкрився лише через ~1 с: спершу потрібно накопичити таймаути. У half-open opossum пропускає
один пробний виклик. Типове `volumeThreshold` в opossum 10.0.0 дорівнює 0, тобто breaker
відкривається на першій же невдачі (видно в `lib/circuit.js`).

### 6. Алгоритми rate limiting (`ratelimit-algos.mjs`, ліміт 10 за 1 с)

| алгоритм | flood: прийнято | макс. за будь-яку 1 с | макс. за 100 мс | атака на межу вікна: макс. за 100 мс |
| --- | ---: | ---: | ---: | ---: |
| fixed window | 40 | 20 | 10 | 20 |
| sliding log | 30 | 10 | 10 | 10 |
| sliding window counter | 35 | 15 | 10 | 10 |
| token bucket (burst 10) | 39 | 19 | 10 | 10 |
| token bucket (burst 1) | 30 | 10 | 1 | 1 |
| GCRA (T = 100 мс, τ = 900 мс) | 39 | 19 | 10 | 10 |
| leaky bucket як черга (вихід) | 40 | 10 | 1 | 1 (затримка до 990 мс) |

flood: 1 запит/мс з 500 до 3500 мс. Атака на межу: 10 запитів на 990 мс і 10 на 1000 мс.

### 7. Розподілений лічильник на Valkey (`ratelimit-redis.mjs`)

10 з'єднань імітують 10 інстансів, 500 одночасних запитів, ліміт 100:

| реалізація | прийнято |
| --- | ---: |
| `GET` + `SET` (read-modify-write) | 500 |
| `INCR`, потім `EXPIRE`, якщо перший | 100 (рахує правильно) |
| Lua: `INCR` + `PEXPIRE` | 100 |
| token bucket у застосунку: `HMGET` + `HSET` | 500 |
| token bucket у Lua | 100 |
| rate-limiter-flexible `RateLimiterRedis` | 100 |

- Інстанс помер між `INCR` і `EXPIRE`: `TTL = -1`, ключ вічний, користувач заблокований назавжди.
- `PEXPIRE` на кожному запиті (ліміт 10/с, клієнт 5/с протягом 6 с): прийнято 10 з 30.
- rate-limiter-flexible рахує фіксоване вікно від першого запиту ключа: атака на його межу дала
  19 прийнятих за 60 мс при ліміті 10/с.
- Сховище недоступне: без `insuranceLimiter` `consume` кидає `Redis connection is not ready`
  (рішення fail-open чи fail-closed лишається за кодом); з in-memory `insuranceLimiter` на 5/с
  пропущено 5 з 8.

### 9. Утилізація і латентність на одному event loop (`utilisation.mjs`)

Сервер (окремий процес) палить CPU Exp(4 мс) на запит, місткість ≈ 250 rps; клієнтська латентність:

| ρ (номінальна) | rps | середня, мс | p50, мс | p99, мс | M/M/1 S/(1−ρ), мс |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0,5 | 125 | 8,5 | 6,0 | 34,2 | 8,0 |
| 0,7 | 175 | 15,5 | 10,3 | 74,8 | 13,3 |
| 0,8 | 200 | 18,6 | 13,8 | 76,3 | 20,0 |
| 0,9 | 225 | 41,3–47,5 | 27–35 | 184–205 | 40,0 |
| 0,95 (90 с) | 238 | 193,8 | 119,4 | 781,7 | 80,0 |

Перші рядки з 20-секундних прогонів, 0,9 з двох прогонів (20 і 90 с), 0,95 з 90-секундного.
На 0,95 факт гірший за модель: розбір HTTP додає до часу обслуговування, тож реальна утилізація
ближча до 1. 20-секундний прогін на 0,95 дав середню 46 мс: на високій утилізації короткі
прогони не сходяться.
