# Оркестрована сага на MongoDB

Код експерименту, на який спирається нотатка
`Obsidian Vault/Engineering/General/System design/Саги й розподілені транзакції.md`
(позначки «перевірено»).

Прогін 2026-10-30: Node v24.14.1, драйвер `mongodb` 7.7.0, MongoDB 9.0.4 (`mongo:9`,
replica set з одного вузла, бо учасники використовують локальні транзакції).

Модель: замовлення → `reserve` (склад) → `charge` (оплата) → `ship` (доставка). Кожен
«сервіс» пише лише у свою базу (`saga_inventory`, `saga_payments`, `saga_shipping`), а
оркестратор тримає журнал саги (`done`, `toCompensate`, `compensated`, `state`) у
`saga_orders.sagas`. Кроки учасників ідемпотентні за ключем саги (`_id` резерву й запису в
журналі оплат) і виконуються локальною транзакцією «ефект + ключ».

## Запуск

```bash
docker run -d --rm --name saga-mongo -p 127.0.0.1:27043:27043 mongo:9 --replSet rs0 --bind_ip_all --port 27043
sleep 7
docker exec saga-mongo mongosh --quiet --port 27043 --eval 'rs.initiate({_id:"rs0",members:[{_id:0,host:"localhost:27043"}]})'
npm ci
MONGO_URL='mongodb://localhost:27043/?replicaSet=rs0' npm run saga   # код виходу 0 = усі 12 перевірок пройшли
docker rm -f saga-mongo
```

## Сценарії й результати (2026-10-30)

| # | Сценарій | Результат |
| - | -------- | --------- |
| 1 | `ship` відмовляє бізнес-помилкою (`UNDELIVERABLE`) | компенсації у зворотному порядку: `refund`, потім `release`; склад 5, баланс 1000. У журналі оплат лишились обидва записи: `REFUNDED:100, REFUND:-100`. Компенсація не стирає списання, а додає нову операцію |
| 2a | читач посеред саги (після `charge`, до `ship`) | наївний звіт за журналом оплат бачить виручку 100 і склад 4; сагу потім скасовано. Звіт, що рахує лише замовлення `APPROVED`, бачить `APPROVED=0, PENDING=1`: семантичне блокування працює, якщо читач його поважає |
| 2b | сага B повністю проходить між кроками саги A, A компенсує | компенсація записом знімка (`$set: {available: 5}`) затерла списання B: `available=5` + 1 у резерві = **6 одиниць з 5**. Комутативна компенсація (`$inc: +1`) дала 4 + 1 = 5 |
| 3 | оркестратор падає після `refund`, до запису «компенсовано» в журнал саги | журнал: `state=COMPENSATING, compensated=[]`; відновлення повторює `refund`. Ідемпотентний (перехід статусу `CHARGED → REFUNDED` + детермінований `_id` повернення): баланс 1000, сага `CANCELLED`. Без ключа: баланс **1100**, два записи `REFUND` |
| 4 | PSP відповідає за 300 мс, таймаут оркестратора 100 мс | **naive** (таймаут = відмова): сагу скасовано, склад повернуто, а пізнє списання пройшло: замовлення `CANCELLED`, баланс **900**. **retry** з тим самим ключем: друга спроба списала, пізня перша отримала duplicate, одне списання, замовлення `APPROVED`. **abort** з надгробком: `refund` без списання записав `VOID` під ключем списання, пізня спроба отримала `CHARGE_VOIDED`, баланс 1000 |
| 5 | `refund` відмовляє постійно (PSP 503) | після 3 спроб сага в `NEEDS_ATTENTION`, запит «застряглих саг» її знаходить. Резерв складу ще не знято, бо компенсації йдуть у зворотному порядку й зупинились на першій невдалій |

## Що тут навмисно спрощено

- «Сервіси» це функції в одному процесі з окремими базами, а не окремі процеси з брокером.
  Між оркестратором і учасниками немає outbox: виклик синхронний, а надійність дає журнал
  саги плюс ідемпотентні кроки. У продакшені команди й відповіді йдуть через outbox/inbox.
- Таймаут змодельовано `Promise.race`: запит, що «вже в дорозі», завершується сам, як і
  справжній HTTP-виклик, на який клієнт перестав чекати.
- Сценарій 1 навмисно ставить `ship` після `charge` з бізнес-відмовою, щоб показати
  ланцюжок компенсацій. Правильний дизайн перевіряє адресу до списання: тоді `charge` стає
  pivot, а `ship` лише повторюваним кроком.
