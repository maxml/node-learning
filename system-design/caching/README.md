# Приклади: кешування в застосунку, Redis і Valkey

Код експериментів, на які спираються позначки «перевірено» в нотатках
`Obsidian Vault/Engineering/General/System design/Кешування в застосунку.md` і
`Obsidian Vault/Engineering/General/System design/Redis і Valkey.md`.

| Файл                  | Що перевіряє                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------- |
| `stampede.js`         | 200 одночасних запитів на ключ, якого немає в кеші, 4 «інстанси» сервісу: без захисту, single-flight, single-flight + lease у кеші, stale-while-revalidate |
| `xfetch.js`           | безперервний потік 500 запитів/с на гарячий ключ: звичайний TTL проти XFetch (Vattani et al., VLDB 2015) з β = 0,5 / 1 / 2 |
| `race.js`             | гонки cache-aside з керованим перемежуванням: читач-промах проти писача, оновлення кешу двома писачами, delayed double delete, lease, версія + надгробок |
| `replication_loss.js` | primary + replica: підтверджений запис губиться після failover; `WAIT`; `min-replicas-to-write`             |
| `eviction.js`         | `maxmemory` 14 МБ: `noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`; роздільність годинника LRU    |
| `blocking.js`         | однопотокове виконання: затримка інших клієнтів під час `KEYS`, `SCAN`, `DEL` і `UNLINK` великого ключа     |
| `lib.js`              | підключення, «БД»-імітація з лічильником викликів                                                          |
| `run.sh`              | повний прогін з підняттям і прибиранням контейнерів                                                        |

## Запуск

Потрібні Docker і Node.js 24. Залежність одна, `redis` (node-redis) 6.3.1, ставиться лише в цю теку.
Порти 56391–56394 на 127.0.0.1 (6379 на хості може бути зайнятий).

```bash
./run.sh            # усе: ~6 хвилин, контейнери sdc-* і мережа sdc-net прибираються в кінці
```

Поштучно:

```bash
docker network create sdc-net
docker run -d --rm --name sdc-cache -p 127.0.0.1:56391:6379 valkey/valkey:9.1.3 valkey-server --save '' --enable-debug-command yes
docker run -d --rm --name sdc-redis -p 127.0.0.1:56394:6379 redis:8.10.3 redis-server --save '' --enable-debug-command yes
npm ci
node stampede.js
node xfetch.js; BETA=0.5 node xfetch.js; BETA=2 node xfetch.js
node race.js
node replication_loss.js; IMAGE=redis:8.10.3 node replication_loss.js   # сам піднімає й прибирає sdc-primary/sdc-replica
node eviction.js; PAUSE_MS=0 POLICIES=allkeys-lru,allkeys-lfu node eviction.js
CACHE_URL=redis://127.0.0.1:56394 node eviction.js
node blocking.js; CACHE_URL=redis://127.0.0.1:56394 node blocking.js
docker rm -f sdc-cache sdc-redis; docker network rm sdc-net
```

## Результати прогону 2026-10-30

Valkey 9.1.3 (`valkey/valkey:9.1.3`), Redis 8.10.3 (`redis:8.10.3`), Node v24.14.1, `redis` 6.3.1,
Docker 29.7.2, один хост. Мілісекунди залежать від заліза й шуму; стабільні лічильники
(виклики БД, вижилі ключі, втрачений запис) повторювались між прогонами.

### Stampede (`stampede.js`, Valkey 9.1.3)

200 запитів, 4 інстанси (по 50 запитів кожному), «БД» відповідає за 100 мс.

| Стратегія                          | Викликів БД | Одночасно в БД | p50 / max латентність |
| ---------------------------------- | ----------- | -------------- | --------------------- |
| cache-aside без захисту            | 200         | 200            | 110 / 113 мс          |
| single-flight у процесі            | 4           | 4              | 102 / 102 мс          |
| single-flight + lease у кеші       | 1           | 1              | 108 / 108 мс          |
| stale-while-revalidate             | 1 (у фоні)  | 1              | 3 / 5 мс              |

Single-flight рятує в межах процесу: викликів БД рівно стільки, скільки інстансів. Lease
(`SET lease:k token NX PX 2000`) зводить флот до одного виклику, а SWR ще й прибирає очікування.

### XFetch (`xfetch.js`, Valkey 9.1.3)

500 запитів/с протягом 12 с на один ключ, TTL 2 с, перерахунок 200 мс; без single-flight і замків.
«Епізод» — пачка викликів БД, що почались у межах 200 мс.

| Політика        | Викликів БД | Епізодів | Викликів на епізод (сер / макс) | Запитів чекали на промаху |
| --------------- | ----------- | -------- | ------------------------------- | ------------------------- |
| звичайний TTL   | 503         | 5        | 100,6 / 101                     | 503                       |
| XFetch, β = 0,5 | 40          | 6        | 6,7 / 15                        | 0                         |
| XFetch, β = 1   | 25          | 10       | 2,5 / 5                         | 0                         |
| XFetch, β = 2   | 71          | 29       | 2,4 / 8                         | 0                         |

Звичайний TTL дає стадо ≈ швидкість × час перерахунку (500/с × 0,2 с = 100). У ранніх прогонах
того ж дня XFetch β = 1 дав 16–26 викликів, макс. 3–8 на епізод. β більше означає раніше й частіше
оновлювати (більше викликів, менші пачки), β менше — ближче до строку, пачки більші.

### Гонки інвалідації (`race.js`, Valkey 9.1.3)

| Сценарій                                                                  | Результат                                     |
| ------------------------------------------------------------------------- | --------------------------------------------- |
| A. читач промахнувся, прочитав v1; писач записав v2 і зробив `DEL`; читач `SET v1 EX 3600` | БД = v2, кеш = v1, TTL 3600 с: застаріле на годину |
| B. два писачі оновлюють кеш замість видалення: у БД v2→v3, у кеші v3→v2     | БД = v3, кеш = v2                             |
| C. delayed double delete (друге `DEL` через 300 мс), читач гальмує 100 мс  | кеш порожній: виправлено                       |
| C. те саме, читач гальмує 600 мс                                          | кеш = v1, TTL 3600 с: не виправлено           |
| D. перемежування A з lease-токеном (Lua: `SET` лише з дійсним токеном; `DEL` анулює lease) | запис читача відхилено, кеш порожній  |
| E. перемежування A з версією рядка й надгробком замість `DEL`              | запис версії 1 відхилено, у кеші надгробок v2 |

### Втрата запису при failover (`replication_loss.js`)

Однаково на Valkey 9.1.3 і Redis 8.10.3:

```
SET order:1 → OK;  WAIT 1 1000 → 1
[розрив мережі до репліки] SET order:2 → OK
WAIT 1 500 → 0
на primary GET order:2 → paid          (WAIT не відкочує запис)
docker kill primary; на репліці REPLICAOF NO ONE
GET order:1 → paid,  GET order:2 → (nil)   ← підтверджений запис втрачено
---
CONFIG SET min-replicas-to-write 1, min-replicas-max-lag 2; репліка заморожена 4 с
SET b → NOREPLICAS Not enough good replicas to write.   (читання працюють)
```

Методична примітка: перша версія імітувала відставання `docker pause`, і запис «виживав»:
ядро далі приймає байти реплікаційного потоку в буфер сокета замороженого процесу, і після
`unpause` репліка їх дочитує. Справжній розрив (`docker network disconnect`) ці байти губить.

### Витіснення (`eviction.js`, `maxmemory` 14 МБ, `maxmemory-samples` 5)

P — 4000 ключів без TTL; гарячий кеш — 1000 ключів з TTL, які читають перед кожною порцією
запису; холодний кеш — 3000 ключів з TTL, яких не читають; потім 12 000 нових ключів з TTL.

| Політика (Valkey 9.1.3) | Нових записів прийнято | P без TTL вижило | гарячий кеш | холодний кеш |
| ----------------------- | ---------------------- | ---------------- | ----------- | ------------ |
| `noeviction`            | 4595 з 12 000, далі `OOM command not allowed…` | 4000 | 1000 | 3000 |
| `allkeys-lru`           | 12 000                 | 433              | 1000        | 446          |
| `volatile-lru`          | 12 000                 | 4000             | 1000        | 95           |
| `allkeys-lfu`           | 12 000                 | 1829             | 1000        | 1904         |

Redis 8.10.3: та сама картина (`allkeys-lru` 409 / 1000 / 295, `volatile-lru` 4000 / 1000 / 89,
`noeviction` прийняв 4194).

- **`volatile-lru` після вичерпання ключів з TTL.** Ключі без TTL дописувались, доки не
  з'явився OOM: Valkey прийняв 8736, і ключів з TTL лишилось 0; Redis прийняв 7249, а OOM
  настав, коли ключів з TTL лишалось ще 961 (у двох окремих прогонах 694 і 927). Причину в
  сирцях Redis не досліджено; висновок практичний: `volatile-*` не обіцяє витіснити весь кеш до
  останнього ключа, перш ніж відмовити в записі.
- **Годинник LRU має роздільність 1 с** (`LRU_CLOCK_RESOLUTION = 1000` у
  `src/lrulfu.c` Valkey і `src/evict.c` Redis). З `PAUSE_MS=0` весь прогін триває пару секунд,
  і `allkeys-lru` зберіг лише 695 з 1000 гарячих ключів при 2096 з 3000 холодних, тобто
  поводився майже як випадкове витіснення. LFU (лічильник частоти) у тому ж прогоні зберіг усі
  1000 гарячих.

### Блокування (`blocking.js`, 2 000 000 ключів)

| Операція                              | Valkey 9.1.3                       | Redis 8.10.3                       |
| ------------------------------------- | ---------------------------------- | ---------------------------------- |
| `KEYS key:1999*` (одна команда)       | 128 мс; PING інших чекав 127 мс    | 312 мс; PING інших чекав 311 мс    |
| `SCAN … MATCH key:1999* COUNT 1000`   | 1031 мс сумарно, 1997 викликів; макс. PING 8 мс | 1421 мс, 2000 викликів; макс. PING 12 мс |
| `DEL` множини з 1 000 000 елементів   | 1 мс (`lazyfree-lazy-user-del yes`) | 115 мс; PING чекав 115 мс (`lazyfree-lazy-user-del no`) |
| `UNLINK` тієї ж множини               | 1 мс                               | 1 мс                               |

Ранній прогін того ж дня: `KEYS` 268 мс (Valkey) і 404 мс (Redis), `DEL` на Redis 163 мс.
