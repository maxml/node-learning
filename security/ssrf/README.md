# SSRF: які обхідні прийоми реально спрацьовують проти наївної перевірки

Код для розділу «Перевірено експериментом» нотатки
`Obsidian Vault/Engineering/General/Security/SSRF.md`.

Docker-мережа з внутрішнім сервісом `internal-admin` (віддає фейковий секрет) і
Node 24 «fetcher», який ходить за URL, що йому дали. Три варіанти перевірки у
`fetcher.js`:

- `/naive` — чорний список рядка-хоста (як пишуть першим);
- `/resolvecheck` — резолвить ім'я, перевіряє, що IP публічний, **потім** `fetch()`
  (який резолвить ім'я вдруге) — вразливий до TOCTOU;
- `/safe` — резолвить **один раз**, відхиляє приватний/loopback/link-local IP,
  і підключається до **зафіксованого IP**, не йдучи за редиректами.

## Запуск

```bash
bash run.sh      # піднімає мережу й контейнери, виводить результати, усе прибирає
```

Потрібен лише Docker; образи `node:24` і `python:3.12-slim`. Секрети фейкові.

## Результати 2026-10-29 (Node v24.22.2)

| Вхід у fetcher | `/naive` (чорний список) | `/safe` (резолв раз + pin) |
| --- | --- | --- |
| `http://internal-admin/` | BLOCKED (хост у списку) | BLOCKED (`resolved to private 172.18.0.2`) |
| `http://127.0.0.1/` | BLOCKED | — |
| `http://2886860802/` (десятковий IP) | **BLOCKED** — див. нижче | BLOCKED (`resolved to private`) |
| `http://public-site/redirect?to=http://internal-admin/` (open redirect) | **BYPASS → 200, секрет витік** | BLOCKED на перевірці |
| `http://rebind.test/` через DNS-rebinding | (не тестовано на naive) | BLOCKED (pin на `192.0.2.1` → timeout) |
| `http://[::ffff:127.0.0.1]/` | — | BLOCKED |

DNS-rebinding проти `/resolvecheck`:

```
resolvecheck http://rebind.test/  ->  {"blocked":false,"checkedIp":"192.0.2.1","status":200,
                                        "body":"INTERNAL-ADMIN-SECRET: fake-token-..."}
```

Лог DNS-сервера підтверджує TOCTOU: перша A-відповідь публічна, друга внутрішня.

```
q rebind.test. type=28 -> (empty)     # AAAA: порожньо, резолвер падає на A
q rebind.test. A#1 -> 192.0.2.1        # перевірка побачила публічний IP
q rebind.test. A#2 -> 172.18.0.2       # fetch() підключився до внутрішнього
```

## Що саме доведено (vs документація)

- **Open redirect — реальний обхід (відтворено).** Наївна перевірка дивиться на
  URL, який дав користувач; `fetch()` із `redirect: follow` пішов за `302` на
  `internal-admin` і витягнув секрет. `/safe` із `redirect: manual` відмовляється.
- **DNS rebinding / TOCTOU — реальний обхід (відтворено).** Перевірка «резолвни й
  переконайся, що IP публічний» проходить, бо між перевіркою та `fetch()` ім'я
  резолвиться вдруге і повертає внутрішній IP. Фікс — pin: `/safe` підключився до
  того IP, який перевірив (`192.0.2.1`), і отримав timeout, а не секрет.
- **Альтернативні кодування IP у Node — НЕ обхід через `new URL()`** (важливий
  нюанс, перевірено окремо): WHATWG-парсер URL у Node канонізує
  `http://2886860802/` → `172.18.0.2`, `http://0x7f.1/` і `http://0177.0.0.1/` і
  `http://127.1/` → `127.0.0.1`. Тому регексп по `url.hostname` їх ловить. Цей
  клас обходу реальний у мовах/парсерах, що **не** нормалізують (наївний split
  рядка, Python до строгого парсингу тощо), а в Node залишковий розрив — це
  **IPv6-mapped** форма: `http://[::ffff:7f00:1]/` лишається у IPv6-записі
  (`[::ffff:7f00:1]`), і IPv4-регексп її пропускає. Тому `isPrivateIp` у
  `fetcher.js` окремо розгортає `::ffff:` перед перевіркою.
- **IPv6-mapped loopback на `/safe`**: заблоковано, але в цьому стенді `dns.lookup`
  повернув `ENOTFOUND` для `[::ffff:127.0.0.1]` раніше, ніж спрацював
  `isPrivateIp`, тож саме логіку розгортання `::ffff:` перевірено окремим
  прогоном `new URL()`, а не цим запитом.
