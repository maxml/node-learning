# Scenario: refactoring a pricing method full of business rules

Backs the note `Obsidian Vault/Engineering/General/Сценарні задачі/Рефакторинг методу з бізнес-правилами.md`.

> A NestJS service contains a 600-line method that calculates pricing and eligibility. It has
> many nested if statements based on customer type, country, product category, contract terms,
> and promotional rules. It also queries the database, modifies entities, and sends
> notifications. Every new rule makes the method harder to change, and …

The experiment shows the safe path: pin current behaviour with a characterization test
(golden master) over the full input matrix, check the safety net with mutation testing,
split the method into a pure `decide()` and an imperative shell (transaction + outbox +
audit), express the rules as tables, then roll out through Branch by Abstraction with a
shadow (parallel) run behind a flag.

Environment of the 2026-10-31 run: Node.js 24.14.1 (TypeScript runs through Node's built-in
type stripping, no build step), Linux 6.8. npm packages, exact versions: @stryker-mutator/core
and @stryker-mutator/tap-runner 10.1.1, TypeScript 7.0.2 as `@typescript/native` (for
`tsc --noEmit`) and 6.0.2 as `typescript` (compiler API for Stryker and sonarjs), @types/node 24.19.2, eslint 10.14.0, eslint-plugin-sonarjs 4.2.2. The machine is shared, so
durations are noisy; all counts are deterministic.

## Run

```bash
npm ci
npm test                 # 17 tests
npm run typecheck        # tsc --noEmit (TS 7)
npm run coverage         # legacy method under the characterization test
npm run mutation         # Stryker on the legacy method, full matrix (~2.5 min)
npm run mutation:coarse  # same, matrix without boundary values (~1.5 min)
npm run mutation:core-golden-only   # Stryker on the new core, golden master only
npm run mutation:core    # Stryker on the new core, golden master + unit tests
npm run rounding-diff    # what switching to exact integer rounding would change
npm run complexity       # cyclomatic / cognitive complexity, legacy vs new
npm run approve          # re-record the golden master from legacy (only for a deliberate change)
npm run golden:show -- '^edge'   # print golden lines by key regex
```

Manual mutations for two claims Stryker cannot generate (script kept outside the repo):
running the outbox test scenario against the legacy (notify-before-commit) shell sends 2
messages where the test expects 0; a shadow router whose candidate calls the full new shell
(with effects) makes `sideEffectsDiffer` 7 560 where the test expects 0. Both tests would go red.

## Tooling notes

- Stryker 10.1.1 with plain `typescript@7.0.2` crashes: `ts.parseConfigFileTextToJson is not a
  function` (its tsconfig preprocessor uses the compiler JS API, which native TS 7 does not
  ship). eslint-plugin-sonarjs 4.2.2 fails for the same reason (`TypeFlags` undefined in
  `ts-api-utils`). Fix used here, as in `design/patterns/`: `typescript` →
  `npm:@typescript/typescript6@6.0.2` for tools, `@typescript/native` → `npm:typescript@7.0.2`
  provides `tsc`.
- Node's type stripping needs erasable syntax only: no decorators, enums or parameter
  properties, so the "NestJS" services here are plain classes with constructor injection.
- `npm run complexity` uses `module.stripTypeScriptTypes`, which prints an ExperimentalWarning
  on Node 24.14.1.
- The golden master is gzipped to keep the repo small; in a real project you would commit
  it as text (or split it per dimension) so the PR diff is reviewable.
