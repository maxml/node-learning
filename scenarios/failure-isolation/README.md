# Сценарій: каскадна відмова через повільний сервіс

Код за позначками «перевірено» в нотатці
`Obsidian Vault/Engineering/General/Сценарні задачі/Каскадна відмова через повільний сервіс.md`.

Умова (assessment-платформа): API на NestJS викликає три внутрішні сервіси; один сповільнюється з
200 мс до 20 с; запити накопичуються, з'єднання з БД зайняті довше, ECS-таски їдять пам'ять,
автоматичні ретраї додають трафіку, падають і здорові сервіси.

## Що тут відтворено

- `services.mjs`: три сервіси в одному процесі: customers (A, ~20 мс), inventory (B, ~30 мс),
  loyalty (C, ~200 мс). Адмін-порт перемикає C на 20 с і рахує, скільки викликів до кожного
  прийшло. Сервіси, як і справжні, доробляють запит, від якого клієнт уже відмовився.
- `gateway.mjs`: API (plain `node:http` + `pg` + глобальний `fetch`; NestJS тут нічого не змінює
  в механіці, тому не взятий). Два ендпоінти:
  - `POST /order` (тіло ~17 КБ JSON) потребує A, B і C і пише замовлення в PostgreSQL;
  - `GET /profile` потребує лише БД і A, тобто **не** залежить від повільного C.
- `run.mjs`: відкрите навантаження (50 rps на `/order` + 50 rps на `/profile`, нові запити йдуть
  незалежно від того, чи встигає сервер), клієнтський таймаут 10 с. 3 с прогріву, 10 с
  здорового режиму, потім C стає 20-секундним на 40 с. Запити з прогріву і з останніх 2 с перед
  сповільненням не входять у підсумок.

| MODE | Що робить API |
| --- | --- |
| `naive` | `fetch` без `signal` (дефолти undici: 300 с до заголовків), транзакція БД відкрита (`BEGIN … INSERT`) на час викликів A, B, C; пул `pg` на 10 з'єднань, `connectionTimeoutMillis: 0` (чекати вічно) |
| `retries` | як `naive` + таймаут 5 с на спробу і 3 миттєві спроби на кожен виклик у шлюзі; клієнт теж робить до 3 спроб |
| `retries-notx` | як `retries`, але транзакція БД після викликів: відокремлює посилення ретраями від виснаження пулу |
| `fixed` | дедлайн 1 с на весь запит, таймаут кожного виклику з залишку (C: не більше 500 мс); bulkhead на C (25 одночасних, понад це відмова одразу); circuit breaker opossum на C (50%, мінімум 20 викликів, `resetTimeout` 5 с); без ретраїв; якщо C недоступний, замовлення приймається зі статусом `loyalty_pending` (`degraded: true`); БД лише після викликів, коротка транзакція, `connectionTimeoutMillis` 300 мс; load shedding понад 200 запитів у польоті |

## Запуск

```bash
npm ci
npm run pg:up          # postgres:18.6-alpine на 127.0.0.1:55442
node run.mjs > results.jsonl     # ~6 хв; MODES=fixed node run.mjs для одного режиму
node summary.mjs                 # таблиця нижче з results.jsonl
npm run pg:down
```

Середовище прогону 2026-10-31 (00:22 за Києвом, у JSON це 2026-10-30T22:22Z): Node.js 24.14.1
(undici 7.24.4), PostgreSQL 18.6 у Docker, pg 8.23.1, opossum 10.0.0, Linux 6.8, 12 логічних CPU,
усе на loopback. **Машина спільна і шумна** (load average 7–12 під час прогону через інші
процеси): абсолютні мілісекунди плавають, порядки величин і напрям ні.

Таймлайн шлюзу (секунда від старту: у польоті / RSS МБ / очікувачів пулу):

- `naive`: 11 с 234/162/224 → 21 с 1000/184/1224 → 31 с 1000/216/2212 → 49 с 1000/254/4002.
  У польоті впирається в 1000 = 100 rps × 10 с клієнтського таймауту, а черга до пулу росте
  далі: шлюз тримає роботу для клієнтів, які вже пішли.
- `retries`: 3000 у польоті (100 rps × 3 спроби × 10 с), 8740 очікувачів пулу.
- `fixed`: 25 у польоті до відкриття breaker-а, далі 2–5; сповільнення на 10-й секунді, breaker
  `open` з 16-ї: у 10-секундному ковзному вікні ще лежали успіхи здорового режиму, і частка
  відмов перейшла 50% лише через ~6 с. На 26-й секунді `half` (пробний виклик), він упав, знову
  `open`.

## Що з цього видно

1. **Пул БД стає спільним вузьким місцем для всіх ендпоінтів.** У `naive` транзакція тримає
   з'єднання весь час виклику C, тож 10 з'єднань зайняті 20-секундними викликами, а `/profile`,
   якому C не потрібен, стоїть у черзі до пулу: 2000 з 2000 запитів упали за таймаутом.
2. **Пул насичений навіть у здоровому режимі.** За законом Літтла пулу потрібно
   50 rps × ~0,23 с ≈ 11,5 з'єднань, а їх 10. Тому в `naive` p50 у здоровому режимі 1,3–1,5 с
   замість 0,2 с. У першому прогоні того ж дня (без відсікання прогріву) здоровий p50 був 329 мс
   для `/order` і 149 мс для `/profile`: черга до пулу на межі стійкості, тому числа скачуть.
   Те саме навантаження з транзакцією після викликів (`retries-notx`, `fixed`) дає 209–216 мс.
3. **Пул випадково працює як bulkhead для C.** У `naive` до C дійшло лише 30 викликів за
   40 с: решта застрягла перед пулом. Без утримання транзакції (`retries-notx`) ретраї клієнта й
   шлюзу перемножились: 3 × 3 = **9 викликів C на одне замовлення**, 8540 одночасних запитів на
   C, RSS шлюзу 460 МБ.
4. **Ретраї клієнта множать вхід у шлюз:** 3 запити на кожну логічну дію, 3000 у польоті замість
   1000, пам'ять 374 МБ проти 254 МБ.
5. **Після виправлення** (`fixed`) `/profile` не помітив аварії (p99 50 мс), замовлення
   приймаються деградованими (p50 39 мс після відкриття breaker-а, p99 575 мс: перші ~6 с, поки
   breaker набирав статистику, кожне чекало таймауту 500 мс на C), у польоті не більше 26.
6. **Таймаут на клієнті не зупиняє роботу на сервері.** У `fixed` C мав до 251 одночасного
   запиту, хоча шлюз відпускав кожен через 500 мс: сервіс C не слухає закриття з'єднання і
   доробляє 20-секундну роботу. Захист викликача не лікує сам сервіс C.
7. **Пам'ять не головний сигнал.** За 40 с RSS у `naive` (254 МБ) і `fixed` (251 МБ) майже
   однаковий: V8 росте кроками, і різниця в кілька тисяч об'єктів на ~17 КБ ховається в шумі.
   Явно пам'ять виросла лише з ретраями (374 і 460 МБ). Сигнали, що показали аварію одразу:
   запити в польоті, черга пулу, `idle in transaction`, латентність на залежність.
8. **Event loop тут ні до чого.** Затримка циклу 17–23 мс у всіх режимах, крім `retries-notx`
   (101 мс від 8540 одночасних сокетів). Аварія тримається на очікуванні ресурсів, а не на CPU.

Чого тут немає: ECS, балансувальника й автоскейлінгу (їх наслідки в нотатці виведено з
документації AWS, а не виміряно); відновлення після того, як C знову стане швидким, не
вимірювалось.
