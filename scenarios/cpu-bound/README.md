# Сценарій: CPU-важкі обчислення в Node.js

Код за позначками «перевірено» в нотатці
`Obsidian Vault/Engineering/General/Сценарні задачі/CPU-важкі обчислення в Node.js.md`.

Умова (assessment-платформа): ендпоінт NestJS робить обчислення на ~5 с CPU; функція позначена
`async`, але поки вона працює, інші запити того самого інстансу дуже повільні або падають за
таймаутом. Чому і як переробити.

## Файли

| Файл | Що робить |
| --- | --- |
| `work.mjs` | «важке обчислення»: кількість простих чисел до N = 7 500 000 перебором дільників (~5 с на тихій машині) |
| `async-is-not-a-thread.mjs` | показує, що `async` і навіть `await null` перед роботою не звільняють event loop |
| `server.mjs` | plain `node:http`: `GET /ping`, `POST /heavy` у чотирьох режимах (`MODE=block|chunk|pool|queue`), `GET /stats` з `monitorEventLoopDelay` |
| `worker.mjs` | воркер BullMQ в окремому процесі для `MODE=queue` |
| `bench.mjs` | autocannon на `/ping` (10 з'єднань, 15 с, таймаут 2 с) + відкритий пробник (`/ping` кожні 100 мс) + `/heavy` на 2-й секунді |
| `transfer.mjs` | ціна передачі даних у воркер: structured clone, transfer, `SharedArrayBuffer` |
| `nest/` | NestJS 12: пул як провайдер, `onModuleDestroy`, блокуючий хендлер проти пулу, 503 при повній черзі, `SIGTERM` під час обчислення |

Чому основний замір на `node:http`, а не на Nest: event loop, пул і черга працюють однаково під
будь-яким фреймворком, а Nest додає лише шар DI. Те, що Nest нічого не змінює, перевірено в
`nest/check.mjs` (блокуючий хендлер у Nest зупинив `/ping` на 10,5 с так само).

## Запуск

```bash
npm ci
npm run valkey:up                     # valkey/valkey:9.1.3-alpine на 127.0.0.1:6391, для MODE=queue
node async-is-not-a-thread.mjs
node transfer.mjs
node bench.mjs > results.jsonl        # ~4 хв; CASES=block,pool node bench.mjs для частини
npm run valkey:down
cd nest && npm ci && npm run check    # tsc + check.mjs
```

Середовище прогону 2026-10-31 (00:30–00:37 за Києвом): Node.js 24.14.1, autocannon 8.0.0,
piscina 5.3.2, BullMQ 6.5.2 + ioredis 6.0.0, Valkey 9.1.3; NestJS 12.3.2, TypeScript 5.9.3;
Linux 6.8, 12 логічних CPU (`os.availableParallelism()` = 12). **Машина спільна й завантажена**
(load average 7–14 від інших процесів), тому 5-секундне обчислення тривало 9,7–12 с. Порівнюйте
стовпці між собою, а не з 5 с.

## Результати 2026-10-31

### `async` не робить роботу неблокуючою (`async-is-not-a-thread.mjs`)

Таймер на 0 мс поставлено *до* виклику; обчислення ~0,94 с.

| Варіант | виклик повернувся через | таймер 0 мс спрацював через |
| --- | ---: | ---: |
| `async function` з обчисленням у тілі | 938 мс | 939 мс |
| `await null`, потім обчислення | 0 мс | 936 мс |

Тіло `async`-функції виконується синхронно до першого `await`. Якщо `await` стоїть перед
роботою, виклик повертається одразу, але решта тіла йде мікрозадачею, а мікрозадачі
виконуються раніше за таймери й I/O: цикл однаково стоїть.

### Навантаження на `/ping`, поки йде `/heavy` (`bench.mjs`)

«autocannon» це закрита модель (10 з'єднань, кожне шле наступний запит після відповіді): поки
сервер стоїть, вона просто шле менше, а запити, що впали за таймаутом, у перцентилі не потрапляють.
Тому поруч стоїть «пробник»: `GET /ping` кожні 100 мс незалежно від відповідей, латентність від
моменту, коли запит мав піти. Затримка event loop з `monitorEventLoopDelay({ resolution: 10 })`
містить інтервал вибірки: простий цикл показує ~10 мс.

| Випадок | autocannon: запитів, p99, таймаутів (2 с) | пробник p50 / p99 / max, мс | пробників > 1 с | затримка циклу max, мс | `/heavy` тривав |
| --- | --- | --- | ---: | ---: | --- |
| без `/heavy` | 225 170, 1 мс, 0 | 2 / 3 / 6 | 0 | 11,7 | — |
| `block`: `async`-хендлер | 37 890, **5 мс**, **40** | **2 301 / 9 563 / 9 663** | 88 з 149 | **9 672** | 9,7 с |
| `chunk`: зріз 10 мс + `setImmediate` | 18 096, 19 мс, 0 | 10 / 20 / 37 | 0 | 36 | **19,3 с** |
| `chunk`, 4 `/heavy` одночасно | 17 764, 55 мс, 0 | 29 / 60 / 169 | 0 | 69 | **70,2 с** кожен |
| `pool`: piscina, 4 потоки | 90 600, 5 мс, 0 | 3 / 11 / 17 | 0 | 28 | 11,8 с |
| `pool`, 12 `/heavy` одночасно, 4 потоки + черга 4 | 55 340, 9 мс, 0 | 3 / 14 / 43 | 0 | 30 | 8 × 200 за 14,9–28,9 с; **4 × 503 за 21–47 мс** |
| `queue`: BullMQ, `202` + опитування | 91 076, 5 мс, 0 | 3 / 13 / 14 | 0 | 16 | `202` одразу; у черзі 13 мс, робота 11,9 с, від запиту до результату 12,1 с |

Що видно:

- **`block`.** Затримка циклу дорівнює тривалості обчислення (9,7 с). autocannon показав p99
  5 мс, бо 40 таймаутів у перцентилі не входять, а кількість запитів упала в 6 разів; відкритий
  пробник показав правду: медіана 2,3 с, 59% запитів довші за секунду.
- **`chunk`.** `/ping` живий (p99 20 мс), але саме обчислення вдвічі довше (19,3 с проти 9,7 с),
  бо ділить один потік з 1 200 rps пінгів. Чотири одночасні обчислення по черзі беруть зрізи: p99
  пінгу росте до 60 мс, а кожне обчислення триває 70 с. Нарізка міняє латентність інших запитів
  на латентність самої роботи й не додає жодного ядра.
- **`pool`.** Головний потік вільний (p99 пробника 11–14 мс). При 12 одночасних запитах на пул
  4 + чергу 4 вісім виконались хвилями (14,9 с і ~29 с), а чотири отримали `503` за десятки
  мілісекунд: обмежена черга перетворює перевантаження на швидку чесну відмову.
- **`queue`.** API лише кладе задачу й відповідає `202` з `Location`; обчислення в іншому
  процесі не впливає на пінги. Ціна: клієнт мусить опитувати чи отримати вебхук, і з'являється
  Valkey як ще одна залежність.

Попередження Node `TimeoutNegativeWarning: -1 is a negative number` у stderr бенчмарка походить з
однієї з бібліотек клієнта і на результати не впливає (не розбиралось).

Перший прогін того самого дня (до додавання пробника) дав той самий малюнок: `block` 50 таймаутів
і затримка циклу 10,4 с, `chunk` 18,4 с на обчислення, `chunk` ×4 по 67 с, 12 одночасних на пул
4 + 4: 8 × 200 і 4 × 503 за 8–9 мс.

### Ціна передачі даних у воркер (`transfer.mjs`)

`postMessage` серіалізує синхронно в потоці, що надсилає, тобто в event loop API.

| Що передаємо | `postMessage` блокує відправника | доставлено через |
| --- | ---: | ---: |
| 1 млн об'єктів `{id, price, sku}` (structured clone) | **337 мс** | 1 055 мс |
| `Float64Array` 64 МБ, копія | 33 мс | 68 мс |
| `Float64Array` 64 МБ, transfer (`transferList`) | 0,1 мс | 0,2 мс |
| `SharedArrayBuffer` 64 МБ | 0 мс | 0,1 мс |

Винести обчислення у воркер і передати йому мільйон об'єктів означає повернути третину секунди
блокування в головний потік. Дані краще передавати як типізовані масиви з transfer або не
передавати взагалі (воркер сам читає з БД чи S3 за ідентифікатором).

### NestJS (`nest/check.mjs`, пул 2 потоки + черга 2)

| Перевірка | Результат |
| --- | --- |
| `POST /heavy-block` (`async`-метод контролера, обчислення в ньому) | єдиний `/ping`, відправлений під час обчислення, чекав **10 497 мс** |
| `POST /heavy` через `CpuPoolService` | 182 пінги, p50 1,9 мс, max 8 мс |
| 6 одночасних `POST /heavy` | 2 × 201 за ~10,4 с, 2 × 201 за ~20,5 с, **2 × 503 за 7 мс** (`ServiceUnavailableException`) |
| `SIGTERM` через 1 с після початку `/heavy` | запит у польоті отримав 201, `onModuleDestroy` → `pool.close()` відпрацював, процес вийшов через 8,6 с |

Nest повертає `201` на `@Post()` за замовчуванням; для обчислення, що нічого не створює, краще
`@HttpCode(200)`, а для асинхронного варіанта `202`. Окремо перевірено, що простий пул piscina не
тримає процес живим сам по собі (процес з пулом на 2 потоки без `destroy()` завершився з кодом 0):
`onModuleDestroy` потрібен, щоб не обірвати обчислення посередині, а не щоб процес «не завис».
